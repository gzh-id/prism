# Prism 项目总览

> 从「为什么要做」到「怎么用」，一次讲完。  
> 面向两类读者：想快速上手的你，以及将来坐在你对面的面试官。  
> 文中所有数字都是实测值，不是估计。

---

## 零、一句话概括

**Prism（棱镜）是一个零后端、隐私优先的前端可观测性工具。**

它是一个 5.38 KB 的采集 SDK + 一个纯本地运行的 React 分析看板。数据在浏览器里采集、在浏览器里存储、在浏览器里分析，**全程不经过任何服务器**；需要分享时导出成一份自包含的 HTML 文件，断网双击就能看。

一句话的类比：**它是装在网页里的行车记录仪。**

---

## 一、为什么要做这个项目

### 1.1 它解决的三个真实痛点

中小团队想给线上项目接前端监控时，几乎必然卡在这三个地方：

| # | 痛点                     | 具体表现                                                           |
| - | ---------------------- | -------------------------------------------------------------- |
| 1 | **商业 SaaS 要付费，且数据要出境** | Sentry 免费额度有限，超出后按事件量收费；埋点数据上传到第三方服务器，很多公司的安全评审**直接过不了**       |
| 2 | **自建投入产出比太低**          | 自建要搭一整套：上报接口 + 消息队列 + 时序存储 + 看板 + 告警。为了「看看用户报错时点了什么」而养一套后端，不划算 |
| 3 | **临时排查的周期比问题本身还长**     | 线上突然报一个错，装 SDK、配后台、等数据进来，两天过去了。问题可能已经自己消失了                     |

Prism 的取舍很直接：**干脆不要后端。**

代价是丢失「多用户聚合」和「实时告警」能力。**这是主动放弃的，不是没想到** —— 这一点在面试时讲出来，比功能列表本身更有说服力。

### 1.2 为什么这个题目适合写进简历

| 维度        | 说明                                                                                          |
| --------- | ------------------------------------------------------------------------------------------- |
| **真实需求**  | 不是 todo list、不是电商 demo，是每家做 Web 的公司都真实存在的问题                                                 |
| **技术纵深**  | 触及浏览器底层 API：`PerformanceObserver`、`Resource Timing`、IndexedDB 事务、事件捕获阶段、`CompressionStream` |
| **有取舍可讲** | 每个设计决策都能说出「为什么不那么做」，这才是面试官想听的                                                               |
| **能造轮子**  | 环形缓冲区、稳定采样、虚拟滚动、Canvas 降采样、瀑布图 —— 都是小而完整的算法题                                                |
| **有量化结果** | 5.38 KB / 89.4% 压缩率 / 17 个测试，简历上可以写具体数字                                                     |

### 1.3 主动放弃的东西（重要）

| 放弃的能力   | 原因                                 |
| ------- | ---------------------------------- |
| 多用户聚合分析 | 零后端架构的必然结果。没有服务端，就看不到「全站今天有多少人受影响」 |
| 实时告警    | 同上。没有人守着服务端，就没人发通知                 |
| 长期趋势对比  | 数据存在本地，换浏览器/清缓存就没了                 |

**能诚实地讲出「我放弃了什么、为什么放弃」，比把项目吹得无所不能更能赢得信任。**

## 二、它到底是什么

### 2.1 两个身份

| 部分     | 位置                | 职责            | 规模                     |
| ------ | ----------------- | ------------- | ---------------------- |
| 采集 SDK | `packages/core`   | 嵌进网页里干活       | 1,527 行 / gzip 5.38 KB |
| 分析看板   | `apps/dashboard`  | 把数据画成图表       | 956 行                  |
| 命令行工具  | `packages/cli`    | 还原混淆后的堆栈      | 164 行                  |
| 类型定义   | `packages/shared` | 全项目唯一真相来源     | 242 行                  |
| 演示站点   | `apps/demo-site`  | 故意写坏的页面，用来造数据 | —                      |

> 规模口径：`.ts` + `.tsx` 源码行数，不含 `dist/` 与测试文件。

### 2.2 数据长什么样

所有采集结果统一成三种事件，这是全项目的**唯一真相来源**：

```ts
type PrismEvent = ErrorEvent | PerformanceEvent | NetworkEvent;

interface ErrorEvent {
  type: 'error';
  kind: 'js' | 'resource' | 'promise' | 'blank-screen';
  message: string;
  stack?: string;
  breadcrumbs: Breadcrumb[];   // 报错这一刻冻结的面包屑快照
}

interface PerformanceEvent {
  type: 'performance';
  name: 'FCP' | 'LCP' | 'CLS' | 'INP' | 'TTFB';
  value: number;
  rating: 'good' | 'needs-improvement' | 'poor';
}

interface NetworkEvent {
  type: 'network';
  url: string; method: string; status: number; duration: number;
  timing?: { dns, tcp, ssl, ttfb, download };   // 拿不到就是 undefined，绝不编造
}
```

**为什么类型定义要单独拆一个包**：SDK 和看板各自独立构建，但它们必须对「一个事件长什么样」有完全一致的理解。放在同一个地方，改一处两边同时生效。

### 2.3 一次完整的数据流

```
网页里发生点什么（报错 / 点击 / 请求 / 首屏渲染完成）
        ↓
   插件捕获（errors / webVitals / network / breadcrumbs）
        ↓
   PrismClient.captureEvent()
        ├─ 采样判定（会话级恒定）
        ├─ 脱敏（丢弃敏感参数）
        ├─ beforeSend 钩子（业务方可主动丢弃）
        └─ 推入队列
        ↓
   队列满 50 条 / 浏览器空闲 / 页面隐藏
        ↓
   transport → IndexedDB（按时间索引，超过 5000 条淘汰最老的）
        ↓
   看板读取 → 四个视图渲染
        ↓
   导出 → gzip + Base64 → 内联进 HTML 模板 → 单文件报告
```

### 2.4 「零后端」到底意味着什么

- 采集、存储、分析**全部在浏览器进程内完成**
- 没有任何 `fetch` / `sendBeacon` 上报行为（可以打开 F12 网络面板验证——除了业务自己的请求，SDK 一个都不发）
- 数据归属明确：就在你自己电脑的 IndexedDB 里
- 需要协作时，用**文件**而不是链接来传递

**隐私合规上的意义**：因为是零上报，所以不存在「用户行为数据出境」的问题，安全评审这一关卡直接消失。这是很多公司接不了商业监控的真实原因。

## 四、核心实现：值得讲的 14 个设计点

> 这一节是整份文档的灵魂。**每一个点都能回答面试官那句「你为什么这么做」。**

### 4.1 环形缓冲区：为什么不用数组 push + slice

**问题**：面包屑要保留最近 20 条，满了就丢最老的。

**常见做法**：

```js
breadcrumbs.push(crumb);
if (breadcrumbs.length > 20) breadcrumbs.shift();  // 或 slice(-20)
```

**这里的选择**：定长环形缓冲区，写入时直接覆盖最老的位置。

**为什么**：

- `shift()` 是 O(n)，每次都要搬移整个数组
- `slice()` 更糟，每次都产生一个新数组 → **大量临时对象 → 触发 GC**
- 面包屑在高频场景（滚动、鼠标移动）下会疯狂写入，GC 抖动会直接影响页面性能 —— 一个监控 SDK 反而把页面搞卡了，是最讽刺的事

**代价**：实现稍复杂，需要自己维护写指针和读顺序（`toArray()` 要按时间正序返回）。

### 4.2 稳定采样：为什么不能用 `Math.random()`

**问题**：大流量下不可能 100% 采集，需要采样。

**常见做法**：每条事件来的时候 `Math.random() < rate`。

**这里的选择**：对 `sessionId` 做 djb2 哈希，映射到 0~1，小于采样率就采。

**为什么**：这是最关键的一个点。

独立掷骰子会导致：**同一个会话里，前 5 条上报了，后 3 条被丢了**。看板上看到的行为轨迹就是断的：

```
点击 → 请求 → 【空】→ 报错
```

而排障时最需要的恰恰是**连续轨迹**。采样必须是会话级的恒定决策，同一会话要么全采要么全不采。

**好处**：哈希是无状态的，不需要存任何东西 —— 同一个 `sessionId` 永远算出同一个结果。

### 4.3 脱敏：为什么「打码」比「丢弃」更危险

**问题**：URL 里可能有 `?token=xxx&phone=138...`。

**常见做法**：打码成 `138****0000`。

**这里的选择**：整个参数**丢弃**。

**为什么**：打码后的值仍然可能被反推（尤其手机号、身份证这类有校验规则的数据），而且打码会给人一种「已经安全了」的错觉。**直接丢弃最安全**。

另外两个细节：

- 用**包含匹配**而不是全等，因为字段名千奇百怪：`userToken`、`access_token`、`pay_password` 都要能拦住
- 脱敏在**入库前**做，而不是导出时做 —— 一旦数据以明文形式存在过，就有泄露风险

### 4.4 面包屑必须在报错那一刻冻结

**问题**：报错时要附带「此前的操作记录」。

**常见做法**：事件里存一个引用，等上报时再读缓冲区。

**这里的选择**：`captureException()` 里立刻调用 `getBreadcrumbs()` 生成快照。

**为什么**：缓冲区是环形的，等看板去读的时候，早就被后续操作覆盖了。你看到的会是「报错之后用户干了什么」，完全反了。

### 4.5 `PerformanceObserver` 的 `buffered: true` 不能漏

**问题**：SDK 通常在 `<head>` 里加载，但 FCP/LCP 可能在 SDK 加载完成前就产生了。

**常见做法**：`new PerformanceObserver(cb).observe({ type: 'largest-contentful-paint' })`。

**这里的选择**：加 `buffered: true`，拿历史上已经产生的条目。

**为什么**：不加这个参数，**页面加载快的场景下一条数据都采不到** —— 因为指标比 SDK 先到。这是个隐蔽的、只在特定条件下暴露的 bug。

**另一个细节**：每个 `entryType` 单独 `try/catch`，因为 Safari 对某些类型支持落后，一个类型不支持不能让整个插件挂掉。

### 4.6 资源加载失败：为什么必须监听捕获阶段

**问题**：`<img src="404.png">` 加载失败，要能采集到。

**常见做法**：`window.addEventListener('error', handler)`。

**这里的选择**：`window.addEventListener('error', handler, true)` —— 第三个参数 `true` 表示捕获阶段。

**为什么**：**资源加载失败的 error 事件不冒泡**。它只在捕获阶段传播，冒泡阶段的监听器收不到。这是 DOM 规范里一个反直觉的设计，不知道的话这个 bug 能查一整天。

**如何区分**是资源错误还是 JS 错误：靠 `event.target`。资源错误的 `target` 是那个 DOM 元素（img/script/link），JS 错误的 `target` 是 `window`。

### 4.7 代理 fetch/XHR，绝不读响应体

**问题**：要知道每个请求的状态码和耗时。

**常见做法**：包一层，读 `response.json()` 看看内容。

**这里的选择**：代理 `window.fetch` 和 `XMLHttpRequest.prototype.open/send`，**只读元数据，绝不碰响应体**。

**为什么**：`Response.body` 是一个**一次性流**。你读了，业务代码再读就是空数据 —— 监控 SDK 把业务搞坏了，这是最严重的错误。

另外：用 `function` 而不是箭头函数保留 `this`；XHR 用 `loadend` 收尾，保证成功/失败/中止都能触发。

### 4.8 Resource Timing：拿不到就留空，绝不编造

**问题**：想知道「慢」到底慢在哪一段。

**这里的选择**：从 `PerformanceResourceTiming` 读出五段 —— DNS / TCP / SSL / 等待 / 下载。拿不到就返回 `undefined`。

**为什么**：**跨域资源如果没有 `Timing-Allow-Origin` 响应头，浏览器会把这些字段全部置 0**。这时候如果直接画，会显示「DNS 0ms、TCP 0ms……」，看起来像数据但其实全是假的。

**处理方式**：拿不到时序时，瀑布图就画一根整条（只显示总耗时），并在代码里明确注释「不编造数字」。诚实比好看重要。

### 4.9 为什么用 IndexedDB 而不是 localStorage

|      | localStorage | IndexedDB      |
| ---- | ------------ | -------------- |
| 容量上限 | **5 MB 硬上限** | 按磁盘剩余空间动态分配    |
| 数据结构 | 只能存字符串       | 支持结构化对象        |
| 索引查询 | 不支持          | 支持（可按时间建索引做淘汰） |
| 写入性能 | 同步，阻塞主线程     | 异步             |

监控数据轻松超过 5 MB，localStorage 会直接抛 `QuotaExceededError`。而且要做「超过 5000 条淘汰最老的」，没有索引就得每次全量排序。

**实现细节**：按 `timestamp` 建索引，`evictIfNeeded()` 时只删最老的一批。

### 4.10 单文件离线报告：项目最出彩的一点

**问题**：怎么把分析结果给别人看。

**绝大多数人的答案**：发个链接，让他登录后台。

**这里的答案**：导出一个自包含的 `.html`，JS/CSS/数据全部内联，**断网双击就能看**。

实现是「模板 + 数据」两段式：

1. **构建时**：Rollup 的 `buildEnd` 钩子生成 `report-template.html`，把看板运行时（含 React）内联进去，只留一个数据占位符
2. **导出时**：把压缩后的数据填进占位符，产出完整文件

**实测**：45 条事件的 JSON 是 14.8 KB，gzip 后 **1.6 KB（省 89.4%）**，最终 HTML 236 KB。

压缩用的是浏览器原生的 `CompressionStream('gzip')` —— **零依赖**，不需要引入 pako 或 lz-string。

**踩过的三个坑**（都写在代码注释里了）：

1. 内联 JS 必须转义 `</script>`，否则 HTML 会提前结束脚本块 → 白屏
2. `String.replace` 的替换值**必须写成函数**。替换字符串里 `$&` / `$'` 是特殊模式，React 压缩代码里恰好有这些序列，直接传字符串会把 HTML 片段注入进 bundle 内部
3. 占位符要匹配**完整赋值语句**，因为占位符片段也会作为常量存在于打包后的 bundle 里，只匹配片段会误伤代码

### 4.11 三个手写的轮子

**① 变高行虚拟滚动（124 行）**

错误列表可能有几千条，每行高度还不一样（错误信息长短不同）。

实现：行高缓存 → 前缀和数组 → 二分查找定位可视区间 → `overscan: 6` 上下多渲染几行 → `useLayoutEffect` 测量真实高度（必须在浏览器绘制前修正，否则会闪一帧）。

**② Canvas 折线图（195 行）**

两个关键点：

- **devicePixelRatio**：不处理的话高分屏上线条会模糊。做法是 `canvas.width = cssWidth * dpr`，然后 `ctx.setTransform(dpr, 0, 0, dpr, 0, 0)`
- **LTTB 降采样**：几千个点不可能全画。用 Largest-Triangle-Three-Buckets 算法，分桶后用**叉积算三角形面积**选代表点 —— 这样**峰值会被保留**（简单抽稀会把尖峰抹掉，而尖峰恰恰是最重要的）

**③ 资源瀑布图（181 行）**

五段着色：DNS 灰 / TCP 蓝 / SSL 紫 / 等待橙 / 下载绿。鼠标悬停显示每段毫秒数。

**价值**：「这个接口慢」是一句废话；「慢在服务器处理（等待 1.2s），不是下载」才是可行动的信息。

### 4.12 体积治理：8 KB 预算卡口

监控 SDK 是**要嵌进业务页面**的，每多 1 KB 都在拖慢用户的页面。一个因为监控而拖慢页面的 SDK 是自相矛盾的。

做法：自研 `scripts/check-size.mjs`（因为 `size-limit` 依赖 esbuild，本机装不上），用 Node 内置 `zlib.gzipSync` 算真实 gzip 体积，超过 **8 KB 直接让构建失败**。

**实测**：

| 产物              | 原始       | gzip        | 预算占用  |
| --------------- | -------- | ----------- | ----- |
| ESM（现代工程）       | 14.36 KB | **5.38 KB** | 67.2% |
| IIFE（一行 script） | 14.33 KB | **5.34 KB** | 66.7% |

留出三分之一余量，是给后续加功能留的空间 —— 而不是刚好卡在 8 KB。

### 4.14 SDK 自身的健壮性

这条贯穿所有代码：**所有采集代码都裹在 `try/catch` 里。**

一个监控 SDK 最严重的错误是什么？**它自己崩溃了，然后把业务页面搞挂了。**

所以：

- 每个插件的 `setup()` 单独 try/catch，一个插件挂掉不影响其他插件
- `captureEvent` 最外层兜底，SDK 自身的任何异常都不冒泡到宿主页面
- 环境判空（`document`/`window` 不存在时直接跳过），保证 SSR / Node 测试环境不会崩

### 4.15 Web Vitals：为什么必须在页面隐藏时兜底上报

这是本项目**开发后期自己发现并修掉的一个真实缺陷**，也是最值得讲的一个故事 —— 因为它不是「知识点」，而是「你真的踩过并解决了」。

**症状**：演示流程是「打开演示站 → 点几个按钮造错误 → 立刻点『打开看板查看』」。这样操作下来，看板的性能页**一张图都没有**。但在页面上多停留几秒再切走，数据又正常。

**根因**（`packages/core/src/integrations/webVitals.ts`）：

原来每个指标的处理是「收到 entry → 排一个 `onIdle` 任务 → 空闲时才 `captureMetric`」。空闲调度本意是好的：不和首屏渲染抢主线程。但它有个致命前提 —— **页面得活着。**

用户在加载后 1 秒内点击跳转时，`requestIdleCallback` 还没轮到执行，页面就销毁了。此时：
- `pending` 里的 LCP / CLS / INP 还没转成事件
- client 在 `pagehide` 上注册的 `flush` 确实跑了，但**队列是空的**，什么也没写出去
- 结果就是最后一次的性能数据永久丢失

**难点在第二层**：就算加了「页面隐藏时也上报」，还是丢。因为 `client` 是在**构造函数**里注册 `pagehide → flush` 的，而插件的 `setup()` 在 `init()` 里晚一步调用（`index.ts:46-48`）。事件监听按注册顺序触发，**client 的 flush 一定跑在插件的上报之前** —— 上报出来的指标还没进队列，flush 已经结束了。

**修法**：插件自己在 `pagehide` 里补一次 `client.flush(true)`，并把这个顺序依赖写进注释：

```ts
onPageHide(() => {
  if (pending.size === 0) return;
  flushPending();
  client.flush(true);   // client 自己的 pagehide 比这里先注册，所以必须再补一次
});
```

顺手把三个指标的**合并语义**也理清了 —— 它们各自的天性不一样，不能一刀切：

| 指标 | 模式 | 为什么 |
|---|---|---|
| FCP / TTFB | `once` | 一条就定终身，重复的 entry 不能覆盖首次值 |
| LCP / INP | `max` | 关心的是最差那一次，比已有值小的候选直接丢 |
| CLS | `sum` | 布局偏移是累加的；**值为 0 也要上报**，因为「没有发生跳动」本身就是个好结论 |

**为什么值得为它写测试**：手点很难复现 —— 快慢鼠标结果不一样，属于典型的 flaky bug。于是 `packages/core/test/webvitals.test.mjs` 用假的 `window` / `document` / `PerformanceObserver` 钉住了这个时序：**断言「页面隐藏前一条都没上报」，然后触发 `pagehide`，断言指标落地且 `flush` 被调用**。同时覆盖了保值（max）、累加（sum）、Safari 不支持某个 entryType 不连带拖垮其他指标三条分支。

> 面试话术：「这个 bug 让我学到的是，**空闲调度和生命周期兜底必须成对出现**。只用 `requestIdleCallback` 的监控 SDK，在『用户点完就走』的场景下一定会丢数据 —— 而这类场景恰恰占比很高。」

## 五、现实中能达到什么程度

### 5.1 和现有方案对比

| 能力              | 浏览器 DevTools | Sentry 等 SaaS | 自建监控     | **Prism** |
| --------------- | ------------ | ------------- | -------- | --------- |
| 采集 JS 错误        | ✅            | ✅             | ✅        | ✅         |
| 报错前的行为轨迹        | ❌            | ✅             | ✅        | ✅         |
| Core Web Vitals | ✅            | ✅             | ✅        | ✅         |
| 资源瀑布图分段         | ✅            | 部分            | 部分       | ✅         |
| 需要后端            | ❌            | 云端            | **要自己搭** | **不需要**   |
| 数据是否离开本机        | 否            | **是（出境）**     | 内网       | **否**     |
| 多用户聚合           | ❌            | ✅             | ✅        | ❌         |
| 实时告警            | ❌            | ✅             | ✅        | ❌         |
| 接入成本            | 零            | 中             | **高**    | 一行 script |

**Prism 卡在一个有趣的生态位**：比 DevTools 多了「行为轨迹」和「可分享」，比 SaaS 少了聚合告警但保住了隐私，比自建少了整个后端。

### 5.2 它真正能做的事

- **个人开发 / 小团队**：接一行 script，出问题时打开看板，能看到报错 + 用户操作轨迹 + 性能趋势 + 请求瀑布图。成本为零。
- **安全敏感场景**：金融、医疗、政企这类数据不能出网的环境 —— 商业监控过不了评审，Prism 天然合规。
- **临时排查**：不用申请资源、不用搭环境，接上去看完就走。
- **把问题甩给同事**：导出一个 HTML 发过去，对方不需要任何环境就能看到完整现场。

### 5.3 诚实的局限

| 局限                | 说明                              |
| ----------------- | ------------------------------- |
| 看不到全站全貌           | 只能看「我这台机器、这个浏览器」的数据             |
| 没有告警              | 出问题不会有人通知你，得自己去看                |
| 换设备就没了            | 数据在 IndexedDB，清缓存或换浏览器即丢失       |
| 未做 E2E 测试         | 目前只有 17 个单元测试，没有 Playwright 端到端 |
| sourcemap 路径基准有偏差 | CLI 用多候选回退绕过，没从根上修              |
| Chrome 扩展未做       | 原本规划里可以外挂到任意第三方站点，还在 Roadmap    |

**如果要真的用在生产，还差这三件事**：端到端测试、多会话管理（现在只有单会话）、数据导入合并（把同事导出的报告合并进来一起看）。

## 七、面试怎么讲

### 30 秒版

> 我做了一个零后端的前端可观测性工具。JS 报错时它能记住报错前用户点了什么 —— 这是定位线上问题最关键的信息，5 分钟和 5 小时的差别就在这一点上。
>
> 数据存在浏览器 IndexedDB 里，不上传任何服务器，因为很多公司的安全评审过不了「埋点数据出境」这一关。代价是主动放弃了多用户聚合告警，这个取舍我想过。
>
> 要给别人看的时候导出一个单文件 HTML，断网双击就能看，45 条事件压缩后省了 89%。
>
> SDK 零第三方依赖，gzip 5.38 KB。里面几个地方我自己造了轮子：环形缓冲区、稳定采样、虚拟滚动、Canvas 折线图和瀑布图 —— 都不重，但每个选择我都能说出理由。

### 3 分钟版

在 30 秒版基础上展开三块：

1. **为什么零后端** —— 讲安全评审过不了这个真实原因，讲主动放弃聚合告警
2. **两个最有技术含量的点** —— 稳定采样（为什么不能用 `Math.random`）和资源错误必须捕获阶段监听（error 不冒泡）
3. **怎么保证不拖慢宿主页面** —— 8 KB 体积卡口、环形缓冲避免 GC、`try/catch` 全包裹保证 SDK 崩溃不连累业务

### 高频追问预备

| 面试官问          | 回答要点                                                           |
| ------------- | -------------------------------------------------------------- |
| 为什么不用 Sentry？ | 不是替代关系。SaaS 要付费且数据出境，很多公司过不了评审；Prism 补的是「我要看，但不能传出去」这个场景       |
| 采样会丢数据吗？      | 会丢会话，但不会丢轨迹。稳定采样保证同一会话要么全采要么全不采，轨迹永远完整                         |
| SDK 会影响页面性能吗？ | 三层保障：体积 5.38 KB；环形缓冲避免 GC；所有采集在空闲时执行且全裹 try/catch              |
| 数据存在本地，怎么协作？  | 导出单文件 HTML，断网可看。这是它比「发个链接登后台」更轻的地方                             |
| 为什么不用现成图表库？   | 三个组件加起来 500 行，够用且不引入几百 KB 依赖。而且手写的 LTTB 降采样能保住峰值，通用图表库的抽稀会抹掉尖峰 |
| 最大的技术难点？      | 单文件离线报告。内联 JS 有三个坑（`</script>` 转义、`$&` 特殊模式、占位符误伤），每一个都会导致白屏   |
| 如果要做下一步？      | 端到端测试 + Chrome 扩展（可以外挂到任意第三方站点看瀑布图）+ 多报告合并                     |
