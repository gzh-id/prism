# Prism 使用手册

> 面向第一次上手的人。不懂的地方照着做就行，每一步都写了「输入什么、会看到什么」。

---

## 零、先搞清楚这是个什么东西

一句话：**它是一个装在网页里的「行车记录仪」**。

- 你的网页崩了、卡了、某个接口慢了，它会记录下来
- 记录的内容包括：报错信息、**报错前用户点了什么**、性能指标（加载速度等）、每个网络请求花了多久
- 数据**存在浏览器本地**，不传给任何服务器
- 你在另一个页面（看板）上查看这些记录

它有两部分：

| 部分 | 位置 | 作用 |
|---|---|---|
| 采集 SDK | `packages/core` | 嵌进你的网页里干活，压缩后 6.07 KB |
| 分析看板 | `apps/dashboard` | 一个 React 页面，把数据画成图表给你看 |
| 演示站点 | `apps/demo-site` | 故意写坏的网页，用来造测试数据 |

## 一、最快上手（三条命令）

打开终端（Windows PowerShell 或 Git Bash 都行），**一条一条执行**：

```bash
cd C:\Users\29782\WorkBuddy\2026-10-02-12-04-33\prism

npm run build   # 构建，产出 dist 目录内的文件

npm run serve   # 启动本地服务
```

看到这个输出就成功了：

```
  Prism 本地服务已启动

  演示站点  http://localhost:5173/apps/demo-site/
  看板      http://localhost:5173/apps/dashboard/dist/

  先打开演示站点点几下按钮，再打开看板。
```

**这个终端窗口不要关。** 关了服务就停了。

> 第一次 clone 下来的话，第一次构建之前还要执行一次 `npm install` 装依赖。
> 已经装过就不用管了，`npm install` 重复执行也没坏处。

### 更省事的办法：双击启动脚本

项目根目录有一个 `start-demo.cmd`，**在文件资源管理器里双击它**就会自动完成三件事：

1. 检查 `dist` 是否已构建，没有就先跑一遍 `npm run build`
2. 启动本地服务
3. 帮你打开演示站点页面

窗口关掉，服务才停。

> **注意双击的位置**：必须在**文件资源管理器**（也就是平时看文件夹的那个窗口）里双击。
> 如果是在编辑器、IDE 或聊天工具的文件列表里点它，那只是「查看内容」，不会运行。
>
> 判断方法很简单：双击后应该弹出一个**黑底命令行窗口**并打印启动信息。
> 如果弹出的是编辑器、里面显示脚本源码，那就是点错地方了，不是脚本坏了。

如果双击后黑窗口一闪就没了，说明脚本执行过但中途报错了 —— 打开终端手动跑
`npm run serve`，就能看到完整的错误信息。

### 为什么必须走这一步，不能直接双击 HTML？

这是最容易踩的坑：**IndexedDB 是按「域名」隔离数据的**。

你直接双击 `index.html`，地址栏是 `file:///D:/...`，浏览器认为它的域名是 `null`。
演示站点和看板各自是独立的 `null`，读不到同一份数据 —— 结果就是看板永远是空的。

所以必须让两个页面都在 `http://localhost:5173` 下打开。`npm run serve` 干的就是这事。

## 二、完整演示流程

### 第 1 步：打开演示站点

浏览器访问 <http://localhost:5173/apps/demo-site/>

页面上有六个按钮，逐个点一遍（**每点完一个停一两秒**，让 SDK 有时间写入）：

| 按钮 | 它会干什么 | 去哪儿看结果 |
|---|---|---|
| 抛一个 JS 错误 | 访问 `null.user.name`，触发 TypeError | 看板「错误」页 |
| 抛一个未处理的 Promise | `Promise.reject` 且没有 catch | 看板「错误」页 |
| 加载一张不存在的图片 | `<img src="/xxx.png">` 404 | 看板「错误」页 + 「网络」页 |
| 发一个慢请求 | 请求一个服务端故意延迟 1.2 秒的接口 | 看板「网络」页瀑布图 |
| 模拟白屏 | 清空整个 body | 看板「错误」页（白屏类型） |
| 手动上报一条 | 业务代码里 try/catch 住的错误 | 看板「错误」页 |

**顺便做一件事**：随手在页面上点几下空白处。这个动作会被记成「面包屑」，等下看错误详情时能看到「报错前用户做了什么」。

### 第 2 步：打开看板

点演示站点上那个绿色的「打开看板查看」按钮，或自己访问
<http://localhost:5173/apps/dashboard/dist/>

### 第 3 步：四个 Tab 分别看什么

#### 概览
四张卡片（错误总数、受影响会话数、请求数、慢请求数）+ 一张 LCP 趋势折线图。

- **LCP** = Largest Contentful Paint，最大内容绘制时间，简单说就是「用户多久能看到主要内容」
- 官方标准：< 2.5s 良好（绿），2.5~4s 待改进（黄），> 4s 差（红）
- 折线图上有一条虚线，就是 2.5s 这条达标线

#### 错误
左边是错误列表（用了虚拟滚动，几千条也不卡），点任意一条看右边详情。

**这里是最值钱的部分** —— 详情下方有一条时间线，叫**面包屑**：

```
12:03:41  点击 button.btn-primary
12:03:42  路由跳转 /checkout
12:03:43  网络请求 GET /api/coupon 200
12:03:43  ✕ TypeError: Cannot read properties of null
```

这就是「用户在报错前做了什么」。线上复现 bug 时，这个东西决定了你是 5 分钟定位还是 5 小时。

#### 性能
五个核心指标各一张趋势图：FCP / LCP / CLS / INP / TTFB。

| 指标 | 人话 | 良好阈值 |
|---|---|---|
| FCP | 页面上第一次出现东西的时间 | < 1.8s |
| LCP | 主要内容出现的时间 | < 2.5s |
| CLS | 页面元素乱跳的程度 | < 0.1 |
| INP | 点了之后多久有反应 | < 200ms |
| TTFB | 服务器多久才开始回数据 | < 800ms |

#### 网络
资源瀑布图。每一行一个请求，横向彩色条被拆成五段：

```
灰 DNS 解析 │ 蓝 TCP 连接 │ 紫 SSL 握手 │ 橙 等待响应 │ 绿 下载内容
```

鼠标悬停能看到每段的毫秒数。这样「慢」就不再是一句模糊的话 ——
是 DNS 慢、还是服务器处理慢、还是文件太大，一眼能分出来。

> 注意：跨域的资源如果没有 `Timing-Allow-Origin` 响应头，浏览器只会给你 0。
> 这时候 Prism 会画一根整条而不拆分，**不会编造数字**。这点很重要。

## 三、把结果发给别人

点看板右上角的**「导出离线报告」**。

会下载一个 `.html` 文件。这个文件的特点：

- JS、CSS、数据**全部内联在一个文件里**
- 断网双击也能看，不需要服务器、不需要装任何东西
- 微信、邮件直接发给同事就行

实测：45 条事件的 JSON 是 14.8 KB，gzip 压缩后 1.6 KB（**省了 89.4%**），最终 HTML 235 KB。

想直接看效果，仓库根目录已经有一份生成好的 **`sample-report.html`**，双击就能看。
重新生成它：`npm run sample`

> 这是这个项目最出彩的一个点。面试官问「你怎么把监控数据给同事看」，
> 大多数人的答案是「发个链接让他登后台」，你的答案是「发个文件，断网也能看」。

## 四、接进你自己的项目

### 方式一：一行 script（最快）

```html
<script src="./packages/core/dist/index.global.js"></script>
<script>
  Prism.init({
    release: '1.0.0',
    integrations: [
      Prism.errorsIntegration(),      // JS 错误、资源加载失败、白屏
      Prism.webVitalsIntegration(),   // FCP / LCP / CLS / INP / TTFB
      Prism.networkIntegration(),     // fetch / XHR 请求
      Prism.breadcrumbsIntegration(), // 点击、路由、生命周期
    ],
  });
</script>
```

四个插件按需引，不用哪个就不写 —— 没用到的会被完整 tree-shaking 掉。

### 方式二：自己手动上报

业务代码里 try/catch 住的错误，全局监听是拿不到的，要手动报：

```js
try {
  computeCoupon(order);
} catch (e) {
  Prism.captureException(e, { severity: 'warning' });
}
```

### 常用 API

```js
Prism.addBreadcrumb({ category: 'custom', message: '用户点了支付' });
Prism.flush();        // 立刻写入（不等待）
await Prism.flushAsync();  // 写入完成之后再继续，跳转页面前用它
Prism.clearEvents();  // 清空本地数据
```

> `flush` 和 `flushAsync` 的区别：写 IndexedDB 是异步的，`flush()` 同步返回。
> 「点完按钮立刻跳走」这种场景如果不等写入完成，看板可能读到旧数据，用 `flushAsync()`。

## 五、命令行：还原被压缩的堆栈

线上跑的是压缩后的代码，报错堆栈长这样：

```
at o (index.global.js:1:3000)
```

看不出是哪一行源码。用这个项目自带的 CLI：

```bash
node packages/cli/src/index.ts sourcemap packages/core/dist/index.global.js.map 1 3000
```

输出：

```
src/client.ts:54:17

  52 |
  53 |   addBreadcrumb(breadcrumb) {
> 54 |     this.breadcrumbs.push({ ...breadcrumb, timestamp: Date.now() });
     |                 ^
  55 |   }
```

直接定位到原始源码的行、列，还带上下各 3 行上下文。

## 六、常见问题

### 看板是空的 / 没有数据

按顺序排查：

1. **是不是 `file://` 打开的？** 回到第一节，必须用 `npm run serve`
2. **看板地址和演示站点是不是同一个域名？** 都必须是 `localhost:5173`
3. **是不是浏览器隐私模式？** 部分浏览器隐私模式下 IndexedDB 会被禁用
4. 刷新一下看板页面再试

### 数据混在一起看不清

点演示站点上的「清空本地数据」，然后重新演示一遍。

也可以直接清浏览器的站点数据：F12 → Application → Storage → Clear site data。

### 点不动 / 没反应

打开 F12 控制台看有没有红色报错。SDK 自身出错时会在 `[prism]` 前缀下打印日志（演示站点开了 `debug: true`）。

### 想彻底重新来一遍

```bash
npm run build   # 重新构建
npm run serve   # 重新起服务
```

| 命令 | 作用 |
|---|---|
| `npm install` | 装依赖（首次） |

## 八、30 秒讲稿（面试用）

> 我做了一个零后端的前端可观测性工具。JS 报错它能记住报错前用户点了什么，
> 这是定位线上问题最关键的信息，五分钟的差距和五小时的差距就在这一点上。
>
> 数据采集完存在浏览器 IndexedDB 里，不上传任何服务器 ——
> 这是因为很多公司的安全评审过不了「埋点数据出境」这一关。
> 代价是主动放弃了多用户聚合告警，这个取舍我是想过的。
>
> 需要把结果给别人看的时候，它能导出一个单文件 HTML，
> JS、CSS、数据全部内联，断网双击就能看，
> 45 条事件压缩后省了 89%，实测 235 KB。
>
> SDK 本身零第三方依赖，压缩后 6.07 KB。
> 里面几个地方我自己造了轮子：环形缓冲区、矩阵采样之外的哈希稳定采样、
> 手写虚拟滚动、手写的 Canvas 折线图和瀑布图 —— 都不重，但每个选择我都能说出理由。

## 九、这个项目的边界（诚实说）

- **主动放弃**：多用户聚合与实时告警。零后端架构的必然代价，不是没想到
- sourcemap 里的 sources 路径基准有偏差，CLI 目前用多候选路径回退绕过
- 还没做 Playwright 端到端测试
- Chrome 扩展（可外挂到任意第三方站点看瀑布图）还没做，在 Roadmap 里
