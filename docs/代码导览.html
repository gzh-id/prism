types.ts

packages/shared/src/types.ts · 242 行

全项目唯一的事件模型定义。core 采集、dashboard 展示、cli 还原，三方都从这里 import。

它解决什么问题

这个项目由三个部分消费同一份数据：内核负责采集、看板负责画图、命令行负责还原堆栈。 如果各自定义一遍事件结构，字段名一定会漂移 —— 采集端写 transferSize， 看板端读 transfer_size，这种错编译期查不出来，只会在页面上变成一块空白。

所以这里定了一条硬规矩：任何模块都不许自己重新定义事件结构。 这个文件只放类型和纯函数，不放任何副作用，因此可以被任何环境安全引入。

注意的地方

HTTP 500 不是错误事件
它是一次正常完成的请求，会被记成 status: 500, ok: false 的网络事件， 在「网络」页按状态码筛，而不是在「错误」页找。这个分工是对的，别在面试里说成「漏掉了接口错误」。
网络事件绝不存请求体和响应体
这是「隐私优先」这条承诺最硬的一块。类型里根本没有 body 字段 —— 不是忘了加，是故意不给。
面包屑只在错误事件上携带
如果每条网络事件都挂 20 条面包屑，数据量会翻 20 倍。 只在 ErrorEvent 上放 breadcrumbs 字段。

session.ts

packages/core/src/session.ts · 51 行

零后端架构下，会话只能由 SDK 自己维护。它产出的 sessionId 是整个系统关联数据的唯一线索。

它解决什么问题

有服务端的监控系统靠 Cookie + 服务端会话表来关联网关。这个项目完全没有服务端， 所以「哪些事件属于同一个用户的一次访问」这件事，必须由 SDK 自己在浏览器里定下来。

判定标准想清楚了：一个标签页从打开到关闭，算一次会话。 这个定义直接决定了存储位置该选哪个。

怎么写的

会话 ID 怎么生成

packages/core/src/session.ts 第 22–25 行
22function createSessionId(): string {
23 // Date.now 保证大致有序，随机后缀保证同毫秒内不冲突
24 return `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 10)}`;
25}

Date.now().toString(36) 提供了大致有序的时间前缀（好处是 ID 本身携带时间信息）， 后面拼 8 位随机串是为了解决同一毫秒内开多个标签页会撞 ID 的问题。 最终长度约 20 字符 —— 这个长度对采样哈希的分布质量很关键，见下一页。

读取逻辑，以及那一整层 try/catch

27export function getSession(): SessionState {

41 }
42 }

44 sessionStorage.setItem(SESSION_KEY, JSON.stringify(created));
45 return created;
46 } catch {
47 // 拿不到存储就退化成「每次刷新都是新会话」，功能降级但不报错

sessionStorage 在下面三种环境里访问会直接抛异常： 无痕模式、用户禁用 Cookie、iframe 沙箱。 而 SDK 的底线是不能因为自己出错把宿主页面搞挂， 所以连读存储这件事都裹在 try/catch 里，失败就降级。

注意的地方

为什么必须是 sessionStorage 而不是 localStorage
这是本文件最关键的一个选择。sessionStorage 的生命周期就是「标签页开着」， 关掉即清空 —— 正好等于「一次会话」的定义。而 localStorage 会永久保留， 用户三天后回来访问，SDK 会把他算成同一个会话， 于是看板上「会话时长」变成三天、行为轨迹首尾不接。
降级策略是有意设计的
拿不到存储时不抛错、不静默失败，而是退化成「每次刷新都是新会话」。 功能打折但页面照常工作 —— 这是 SDK 应有的姿态。
每次读取都会回写 lastActiveAt
所以这个字段表示的是「最后一次活跃时刻」而不是「最后一次写入时刻」， 会话时长要用 lastActiveAt - startedAt 算。
面试怎么答

「会话我用 sessionStorage 存，因为它的生命周期恰好等于一次会话。 用 localStorage 会让三天后的访问还算作同一会话，看板数据就串了。 无痕模式下访问存储会抛异常，所以整段逻辑裹在 try/catch 里降级。」

sampling.ts

packages/core/src/sampling.ts · 43 行

决定「这个会话的数据要不要采集」。43 行，零依赖，是整个项目最短也最值得讲的文件。

它解决什么问题

监控 SDK 在高流量站点上必须降采样，否则数据量会失控。 但按什么粒度抽签这件事，抽错了比不抽更糟。

做法结果可不可用
每条事件独立 Math.random()同一会话里采到第 1、2、4、5 条，第 3 条丢了❌ 轨迹断裂
按会话稳定决策整个会话要么全采、要么全丢✅ 轨迹完整

假设采样率 50%，用户在同一个会话里连续做了几个动作。 按事件抽签的话，你在看板上看到的是这样的时间轴： 点击结算 → 请求 /api/cart → 【空】 → 请求 /api/price → 报错。 中间那一步「用户改了数量」不见了 —— 而它很可能恰恰是报错的原因。 排障最需要的连续轨迹，被采样剪碎了。

怎么写的

哈希函数：把任意字符串压成 32 位数

packages/core/src/sampling.ts 第 13–31 行
13/**
14 * djb2 字符串哈希。短小、够快、分布均匀，几行代码就能满足稳定采样需求。
15 *
16 * ⚠️ 一个实测出来的前提：djb2 对「长度很短的输入」几乎没有扩散能力。
17 * 因为对定长输入来说它的结果是线性的，同长度的短 ID 会全部落进同一个桶 ——
18 * 实测 's1' 's2' … 'sz' 的哈希比例全都是 0.00137。
19 * 后果是：如果调用方传进来的 sessionId 只有两三个字符，采样就退化成「要么全采、要么全丢」。
20 * 本项目自产的 sessionId 是 `时间戳36进制-8位随机`（约 20 字符），实测扩散正常
21 * （样本比值从 0.08 到 0.99 均有覆盖），所以不受影响。
22 * 但把它当通用工具复用时，必须保证 ID 有足够的长度和熵。
23 */
24export function hashString(input: string): number {
25 let hash = 5381;
26 for (let i = 0; i < input.length; i += 1) {
27 hash = ((hash << 5) + hash + input.charCodeAt(i)) | 0;
28 }
29 // 转成无符号 32 位，保证后面除法落在 0~1
30 return hash >>> 0;
31}
  • 5381 是 djb2 这个经典算法的推荐种子值，位模式分散
  • (hash << 5) + hash 等于 hash * 33。为什么这么写？因为 33 = 32 + 1，只用移位和加法。现代 JS 引擎里和直接乘 33 性能一样，这里更多是沿用经典写法的习惯 —— 面试被追问时实话实说，比硬扯性能加分
  • input.charCodeAt(i) 让字符参与运算，否则 'abc' 和 'cba' 会得到同一个结果
  • | 0 是防精度丢失：每轮乘 33，算 20 个字符就是 5381 × 33²⁰，远超 JS 能精确表示整数的上限 2⁵³，小数部分就不可信了。JS 位运算强制转 32 位有符号整数，顺便把结果截断回安全范围
  • >>> 0 把可能出现的负数翻译成对应的无符号值，保证后面除以 0xffffffff 得到 0~1

决策函数：只有 4 行，但每一行都有理由

packages/core/src/sampling.ts 第 37–42 行
37export function shouldSample(sessionId: string, rate: number): boolean {
38 if (rate >= 1) return true;
39 if (rate <= 0) return false;
40 const ratio = hashString(sessionId) / 0xffffffff;
41 return ratio < rate;
42}
  • 为什么先处理 0 和 1：不只是省一次哈希。采样率 1 的含义是「100% 都要」，就该无条件 true，不该指望「哈希比值恰好小于 1」。提前返回把这类边界歧义彻底消灭
  • 除数是 0xffffffff（4294967295）而不是 0x100000000：因为 hash >>> 0 的最大值就是它。除以它，比值能完整覆盖 [0, 1] 闭区间；除以 2³² 的话最大值只能到 0.99999999977，理论上有极微小偏差
  • 整个模块是纯函数：没有 Map 记录「哪些会话决定采过」。因为结果由输入唯一决定，不需要记 —— 零内存、不泄漏，新页面加载时重算必然得到同一答案

注意的地方

⚠️ djb2 对短输入几乎没有扩散能力（实测发现）
实测数据：'s1'、's2'、's9'、'sa'、'sz' 的哈希比值全都是 0.00137，全部落进同一个桶。 原因是同长度输入的哈希结果是线性组合，取值范围被锁死在 5381×33² ≈ 5.86M 附近。 后果：如果 sessionId 只有两三个字符，采样会退化成「全采」或「全丢」，功能失灵。 本项目安全 —— 生成的 ID 约 20 字符，实测 8 个样本比值从 0.0817 到 0.9898 覆盖良好 （5000 次、采样率 0.1 实测命中率 9.72%，期望 10%）。
这个前提已经被测试钉住了
测试里同时断言两件事：同长短 ID 的比值极差 < 0.001（钉住已知局限）， 真实长度 ID 的比值极差 > 0.5（钉住采样可用性）。 以后谁想换哈希算法，必须先回答「短 ID 退化」有没有被解决。
采样决策整个会话只算一次
在 client.ts 构造函数里算出 this.sampled 并缓存， 之后每个采集入口都只是判 if (!this.sampled) return。 不理解这点会误以为它被调用了很多次。
面试怎么答

「采样必须按会话做，不能按事件做 —— 按事件抽签会把用户的因果链剪碎， 你看到一个错误却看不到导致它的那次操作。 实现上是对 sessionId 做 djb2 哈希映射到 0~1，纯函数、不存状态。 不过 djb2 对短输入扩散很弱，实测两字符 ID 全落在同一个桶， 所以我保证了生成的 sessionId 有 20 个字符和足够熵，并用测试把这个前提钉住了。」

ring-buffer.ts

packages/core/src/ring-buffer.ts · 53 行

面包屑的存储结构。定长数组 + 一个写指针，写入永远 O(1) 且零内存分配。

它解决什么问题

面包屑是高频写入的 —— 用户每点一次、每发一个请求就写一条， 交互密集的页面上一秒可能写十几条。同时它必须有容量上限， 否则一个长期挂着的标签页会把内存吃光。

最直观的写法是数组加 shift()。问题在于 shift() 会把后面所有元素往前挪一格，是 O(n)； 而 slice(-20) 这类写法每次都会创建一个新数组。 在高频路径上，这等于每秒制造十几个临时数组让垃圾回收器去扫 —— 监控 SDK 自己成了拖慢页面的元凶，这就本末倒置了。

怎么写的

三个字段，各管一件事

13export class RingBuffer<T> {
14 private readonly items: Array<T | undefined>;
15 private writeIndex = 0;
16 private filled = 0;
17
18 constructor(private readonly capacity: number) {
19 this.items = new Array<T | undefined>(capacity);
20 }
21
22 /** 写入一条。写满后自动覆盖最老的那条 */
23 push(item: T): void {
24 this.items[this.writeIndex] = item;
25 this.writeIndex = (this.writeIndex + 1) % this.capacity;
26 if (this.filled < this.capacity) {
27 this.filled += 1;
28 }
29 }
  • items：定长数组，长度就是容量。类型是 Array<T | undefined> —— 刚创建时里面全是空洞，类型上必须诚实标出来
  • writeIndex：下一个该写哪一格，写满后绕回 0
  • filled：已经装了多少条，上限是容量。它为什么必须存在见下面的坑
  • push 里没有任何「先判断格子有没有人」的逻辑 —— 覆盖就是设计本身，不是意外

实测走位（容量 3，依次 push a b c d e）

push d 那一步是关键：a 被 d 直接覆盖， items 变成乱序的 [d,b,c]，而读取从下标 1 开始绕 1→2→0， 得到正序的 b, c, d。 内部存储顺序是乱的，读出来永远是时间正序 —— 看板的时间轴完全依赖这个保证。

注意的地方

filled 不能用 items.length 代替
items 是预分配的定长数组，length 从头到尾都是容量。 另一个更重要的原因：写指针会绕圈，当它回到 0 时你没法判断这是「刚开始写」 还是「已经绕了一整圈」—— 这两种状态要做的事完全不同。 所以环形缓冲天然需要区分填充期（filled < capacity）和稳态期（filled === capacity）。
O(n) 被刻意放在了读取侧
push 是 O(1) 零分配，toArray 是 O(n) 且每次新建数组。 看起来不对称，其实是刻意的：写入高频、读取低频。 toArray 只在 captureException 冻结快照时调用一次。 如果反过来（写的时候 slice），就等于把开销压在了最热的路径上。
容量 20 这个数字的由来
意思是「最多回溯用户报错前的 20 个操作」。 再多会明显加大错误事件的体积 —— 面包屑会随错误一起落盘， 而且导出报告时也一起被压缩进去。
面试怎么答

「面包屑我用环形缓冲存，不是数组。数组方案下 shift 是 O(n) 还要搬移元素， slice 每次都造临时数组，在高频写入路径上会给 GC 很大压力。 环形缓冲是定长数组加写指针，写入 O(1) 零分配。 要注意 filled 这个字段不能省 —— 写指针绕回 0 时，靠它才能区分刚开始写还是已经绕了一圈。」

采集五个核心性能指标。这个文件里有一个「真实踩过并被修掉的缺陷」，是本项目最好的面试素材。

它解决什么问题

性能指标不像错误那样是「事件发生」——它们是持续累积的。 LCP 每出现一个更大的元素就更新一次，CLS 是不断累加的， INP 要取所有交互里最慢的那一次。

所以这个文件真正要解决的不是「怎么拿到数据」，而是 「拿到之后什么时候上报、上报哪一个值」。这两件事必须分开处理。

指标含义累积方式
FCP屏幕上第一次出现内容一条定终身
LCP最大那块内容出现的时间反复更新，取最新
CLS布局偏移累计量（页面乱跳程度）持续累加
INP点击到屏幕有反应的时间取最差的一次
TTFB服务器吐出第一个字节的耗时一条定终身

注意的地方

🔴 绝不读响应体 —— 这是绝对不能做的事
响应体必须读流才能拿到，而流只能读一次。 一旦 SDK 读了，业务代码再读拿到就是空数据。 这是 SDK 放弃第三方页面时最容易踩的坑，而且症状极其诡异 —— 页面看起来正常，但某个接口的数据莫名变成空。

所以这个插件的隐私红线是：只取 URL、方法与时序，绝不碰请求体和响应体。
「代理」和「替换」的区别
代理的意思是：包一层壳记录耗时，然后原样调用浏览器原生方法。 任何对原生 API 的行为改变（哪怕只是少传一个参数、改一下返回值的类型） 都可能让宿主页面直接崩掉。这是 SDK 侵入第三方页面时最基本的礼貌。
同一个 URL 被请求多次时取最后一个 entry
performance.getEntriesByName(url, 'resource') 返回的是数组， 取 entries[entries.length - 1]。 因为性能条目是按时间累积的，最后一次才是刚发出去的那次请求。

18/** 中位数比平均数更能反映「典型体验」，平均数会被少数极端值拉偏 */
19function median(values: number[]): number {
20 if (values.length === 0) return 0;
21 const sorted = [...values].sort((a, b) => a - b);
22 const mid = Math.floor(sorted.length / 2);
23 return sorted.length % 2 === 0 ? ((sorted[mid - 1] as number) + (sorted[mid] as number)) / 2 : (sorted[mid] as number);

手写虚拟滚动，支持变高行。错误列表上千条也不卡。

它解决什么问题

错误列表可能有几千条。全部渲染成 DOM 的话， 光是创建节点就要几秒，滚动时每一帧还要重排全部节点。

虚拟滚动的思路：只渲染可视区域内的那几条， 用「撑高的空 div」让滚动条长度保持正确。 DOM 节点数就被恒定在「可视区条数 + overscan」这个量级。

难点在于行高不固定 —— 错误消息有长有短。 变高行没法直接用 index × 行高 算出位置，必须另想办法。

apps/dashboard/src/LineChart.tsx · 195 行

手写 Canvas 时序折线图，带达标参考线。难点在降采样和高分屏清晰度。

它解决什么问题

为什么用 Canvas 而不是 SVG：数据量上千以后，SVG 的每个点都是一个 DOM 节点， 浏览器光是维护这些节点就会卡住。Canvas 只有 1 个节点， 绘制成本和数据量线性相关。

两个必须处理的细节：高分屏清晰度、以及「点太多但屏幕没那么宽」的浪费。

怎么写的

LTTB 降采样：保留峰值，而不是简单抽稀

27export function lttb(data: Point[], threshold: number): Point[] {
28 if (threshold >= data.length || threshold <= 2) return data;

30 const sampled: Point[] = [data[0] as Point];

32 let a = 0;
33
34 for (let i = 0; i < threshold - 2; i += 1) {
35 // 下一个桶的平均点，用来构成三角形
36 const nextStart = Math.floor((i + 1) * bucketSize) + 1;
37 const nextEnd = Math.min(Math.floor((i + 2) * bucketSize) + 1, data.length);

39 let avgY = 0;

43 avgY += data[j]?.y ?? 0;

46 avgY /= avgCount;

49 const rangeEnd = Math.floor((i + 1) * bucketSize) + 1;

53 let best = rangeStart;
54

屏幕横向只有几百个像素，却要画上万个点，绝大部分点是浪费的。 但抽稀不能乱抽 —— 监控图表里尖峰恰恰是你要看的东西。

LTTB（Largest-Triangle-Three-Buckets）的做法是： 把数据分桶，每桶选一个点，选择标准是「与前后两点构成的三角形面积最大」。 面积最大意味着这个点最能代表局部的形状特征。

第 57 行的注释点出了实现要点：用叉积算三角形面积，省掉开方。 我们只需要比较面积大小，不需要知道具体数值，所以免掉 √ 运算。

注意的地方

简单抽稀会抹掉峰值
如果按固定间隔取点（比如每 10 个取 1 个），一个持续 1 分钟的性能尖峰 很可能刚好落在被丢掉的那 9 个点里。 LTTB 的核心价值就是「保留视觉形状」，尖峰一定会被选中。
数据点只有一个时也要能画
toX 里对 maxX === minX 做了特判。 这类边界在真实数据里经常出现 —— 用户第一次打开页面时， 某个指标就可能只有一个数据点。
阈值线不参与 Y 轴压缩
Math.max(...ys, threshold ?? 0) * 1.15 —— 阈值也要参与最大值计算。否则当所有数据都远低于阈值时， 达标线会被画到画布外面去，图表就失去了参照。

手写资源瀑布图，把每个请求拆成 DNS / TCP / SSL / 等待响应 / 下载 五段。

它解决什么问题

这个图是整个看板里最能直接指导优化的一张。 看到一条请求慢，你立刻能知道是 DNS 慢、建连慢、 服务器响应慢，还是资源太大下载慢。只看总耗时的话，你只能猜。

用 Canvas 而不是 DOM：一个页面几百个请求，每个请求 5 段， 用 DOM 就是上千个节点，滚动会掉帧。

注意的地方

压缩率为什么这么高
监控数据的高度重复性极强：同样的 userAgent、 同样的字段名、大量结构相同的对象。gzip 对这种重复特别有效， 所以实测能到 10%。 这也是为什么「数据量大」在这个项目里不构成致命问题。
测试里有两条断言在保护这个功能

测试的写法：window 上故意不提供 requestIdleCallback，于是它会走 setTimeout 兜底分支， 保证「空闲上报」不会在断言之前偷偷发生。

然后：灌一条 LCP entry → 断言此刻一条都没上报 → 触发 pagehide → 断言指标落地并且 flush 被调用。

最后那条断言尤其重要：它验证了「补一次 flush」这个容易被漏掉的动作。

注意的地方

「测产物而不是源码」是有代价的
必须先 npm run build 才能跑测试。 忘了构建就会测到旧版本 —— 这种「测试通过但测的是旧代码」比测试失败更危险。 所以 npm test 之前要确保构建是最新的。
还没做 E2E
真实的端到端验证（比如「页面触发一个错误，断言 IndexedDB 里确实出现了这条事件」） 需要 Playwright 之类在真浏览器里跑。 这是这个项目目前已知的缺口，也是接下来最值得补的一块。
为什么用 Node 内置 test runner
不额外引入 Jest / Vitest。 node --test 是 Node 20+ 自带的， 零依赖、零配置 —— 和整个项目的取舍风格一致。
