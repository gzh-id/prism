## 第一部分 · `sampling.ts` —— 决定「这个会话要不要采集」

### 1. 它在整条链路里的位置

只有一处调用，在 `client.ts:82`：

```ts
this.sampled = shouldSample(this.session.id, this.options.sampleRate);
```

注意两个细节：

- 它在**构造函数**里算，而且结果存进 `this.sampled`
- 之后每一处采集入口都是先判 `if (!this.sampled) return;`（`client.ts:123`、`197`、`224`）

也就是说：**采样决策在整个会话里只算一次，然后被复用了无数次。** 这是理解这个文件的钥匙。

### 2. 先讲问题：为什么不能「每条事件各掷一次骰子」

假设采样率 50%，用户在**同一个会话**里连续做了 10 个动作，你想让服务器压力减半。

**错误做法** —— 每条事件独立 `Math.random() < 0.5`：

| 顺序 | 动作 | 掷骰结果 | 是否上报 |
| --- | --- | --- | --- |
| 1 | 点击「结算」 | 中 | ✅ |
| 2 | 请求 `/api/cart` | 中 | ✅ |
| 3 | 用户改数量 | 未中 | ❌ 丢了 |
| 4 | 请求 `/api/price` | 中 | ✅ |
| 5 | 报错 `Cannot read …` | 中 | ✅ |

你在看板上看到的是这样的时间轴：

```
点击结算 → 请求 /api/cart → 【空】 → 请求 /api/price → 报错
```

**第 3 步"用户改数量"不见了。** 而这个动作很可能恰恰是导致第 5 步报错的原因。排障时最需要的就是**连续轨迹**，采样却把它剪碎了。

**正确做法** —— 会话级决策：整个会话要么全采，要么全丢。轨迹永远是完整的。

> 面试话术：「采样的粒度选错了，比不采样还糟 —— 不采样你至少知道数据不全，
> 采样错了你会**误以为**这是完整的因果链。」

### 3. `hashString` 逐行（第 13–33 行）

```ts
export function hashString(input: string): number {
  let hash = 5381;
  for (let i = 0; i < input.length; i += 1) {
    hash = ((hash << 5) + hash + input.charCodeAt(i)) | 0;
  }
  return hash >>> 0;
}
```

**`let hash = 5381`** —— djb2 这个经典算法的推荐种子值。换别的数也能跑，但 5381 是经过大量实践验证、分布较好的选择（`5381 = 2^13 + 2^3 + 1`，位模式分散）。

**`(hash << 5) + hash`** —— 这是全文件最"聪明"的一行。`<< 5` 就是乘 32，所以整个表达式等于 `hash * 33`。为什么不直接写 `hash * 33`？因为 `33 = 32 + 1`，用「左移 5 位再加自己」只需要移位和加法，不需要乘法指令，是早期 C 语言留下的经典写法，现代 JS 引擎里两者性能其实一样 —— **面试时如果被追问，实话实说"这里更多是沿用经典写法的可读性/习惯，不是性能差异"，比硬扯性能加分。**

**`input.charCodeAt(i)`** —— 取出每个字符的编码参与运算。**这是让"字符位置"有意义的关键**：如果只做乘法不掺入字符，那 `'abc'` 和 `'cba'` 会得到完全一样的结果。项目里的单元测试就在钉这一点：

```js
assert.notEqual(hashString('prism'), hashString('prizm'));
```

**`| 0`** —— 这一步是**防精度丢失**的。`hash` 每轮都乘 33，算 20 个字符后就是 `5381 × 33^20`，这个数字远超 JS 能精确表示整数的上限 `2^53`，继续算下去小数部分就不可信了。JS 的位运算符（`<<` `|` `&`）**强制把操作数转成 32 位有符号整数**，所以 `| 0` 顺便把结果截断回安全范围，代价是允许中间出现负数。

**`>>> 0`** —— 无符号右移 0 位。作用是**把上一步可能产生的负数翻译成对应的无符号值**（`-1` 会变成 `4294967295`）。不做这一步，后面除以 `0xffffffff` 就会得到负数比值，采样逻辑直接失效。

### 4. 一个实测出来的坑（**这段最值得看**）

djb2 有一个不写在教科书上的前提。我实测出来的数据：

```
s1 → 0.00137        s9 → 0.00137
s2 → 0.00137        sa → 0.00137
s3 → 0.00137        sz → 0.00137
```

**所有两字符的 ID 全都落进了同一个桶。**

原因：对**长度相同**的输入来说，djb2 的结果是各个字符的线性组合，取值范围被死死限制在一个很窄的区间里。两字符输入的哈希值都被挤在 `5381×33² ≈ 5.86M` 附近 —— 而 `5.86M / 4294967295 ≈ 0.00137`。

**后果**：如果调用方传进来的 `sessionId` 只有两三个字符，采样率设成 0.5 会得到「**全部命中**」或「**全部丢弃**」，采样功能等于失灵。

**本项目为什么不受影响**：`session.ts:24` 生成的 ID 是这种格式 ——

```ts
return `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 10)}`;
// 形如：mutc5z3b-gp840a2l  （约 20 字符）
```

实测 8 个真实格式 ID 的比值分布：

```
0.0817  0.2501  0.2622  0.9898  0.5977  0.6170  0.4185  0.6962
```

从 0.08 到 0.99 均有覆盖，扩散良好。**长度和熵都够，所以安全。**

> 这段为什么值得在面试里主动讲：它证明你不是「照着教程抄了个 djb2」，
> 而是**知道它在什么条件下会坏**。如果面试官问「你这个哈希有什么局限」，
> 能立刻答出「短输入扩散弱，所以我保证了 sessionId 长度」——这是明显的分水岭。
>
> 这条前提已经写进源码注释，并且用测试钉住了：
> `core.test.mjs` 里的 `hashString：确定性、取值范围，以及短输入扩散弱这个已知前提`。

### 5. `shouldSample` 逐行（第 23–32 行）

```ts
export function shouldSample(sessionId: string, rate: number): boolean {
  if (rate >= 1) return true;
  if (rate <= 0) return false;
  const ratio = hashString(sessionId) / 0xffffffff;
  return ratio < rate;
}
```

**为什么先处理 0 和 1 两个边界**：不只是为了"省一次哈希计算"。更实际的原因是**避免边界上的语义歧义** —— 采样率 1 的意思是"100% 都要"，那就应该无条件 `true`，而不该指望"哈希比值刚好小于 1"。虽然 `hash >>> 0` 的最大值恰好是 `0xffffffff`，除以自己得 1.0，`1.0 < 1` 是 `false`，会漏掉**那一亿分之一个**会话。提前返回把这类边界问题彻底消灭。

**为什么除数是 `0xffffffff`（4294967295）而不是 `0x100000000`（4294967296）**：因为 `hash >>> 0` 的**最大值**就是 `0xffffffff`。除以它，比值能完整覆盖 `[0, 1]` 这个闭区间；若除以 `2^32`，最大值只能到 `0.99999999977`，理论上有极微小的偏差。差别小到无实际影响，但选哪个更"严丝合缝"是清楚的。

**`ratio < rate`** —— 小于而不是小于等于，配合上面的端点处理，让 `rate=0` 时绝对不可能采到。

### 6. 为什么不需要存任何状态

整个模块是**纯函数**：没有 `Map` 记录"哪些会话决定采过"，没有缓存，没有副作用。

因为「同一个 sessionId 永远得到同一个结果」——**结果是由输入唯一决定的，不需要记。** 这就是所谓的"无状态稳定采样"。

好处很实在：
- **零内存**，不会随会话数增长而泄漏
- **可以跨页面复用**，只要 sessionId 一样（同一标签页内），新页面加载时重新算一遍必然得到同一个答案
- 单元测试里那条 `for (let i = 0; i < 100; i += 1)` 断言 100 次结果一致，就是在保护这个性质

> 顺带一提：这也是为什么 `client.ts` 可以把 `sampled` 存成 `readonly` 字段 ——
> 它从创建到销毁都不会变。

### 7. 这一节可能被追问什么

| 追问 | 怎么答 |
| --- | --- |
| 为什么不用 `Math.random()`？ | 会导致同一会话的轨迹断裂，采样后无法还原因果链 |
| 采样率 0.1 会让小流量站点采不到样本吗？ | 会。所以默认 `sampleRate = 1`，要降采样得先有足够流量 |
| 为什么用 djb2，不用 murmur / xxhash？ | 体积预算 8KB。djb2 只有 5 行，murmur 要几十行，而这里只需要"稳定"不需要"抗碰撞" |
| 哈希冲突了会怎样？ | 这里只关心比值落点，偶发碰撞只是让两个会话采样决策一致，不影响正确性 |
| 采样是采多少？单条事件还是整个会话？ | 整个会话。`sampled === false` 时**所有**事件都不进队列 |

## 第二部分 · `ring-buffer.ts` —— 面包屑怎么存

### 1. 先搞清楚「面包屑」是什么

报错时最有用的信息往往不是堆栈，而是**用户报错前做了什么**。

```ts
export interface Breadcrumb {
  timestamp: number;
  category: 'click' | 'navigation' | 'network' | 'console' | 'lifecycle';
  level: Severity;
  message: string;      // 「点击了 button#checkout」
  data?: Record<string, unknown>;
}
```

看板上的错误详情页里，那个按时间排列的行为时间轴，数据就来自这里。**容量固定 20 条**（`client.ts:30` 的 `DEFAULT_MAX_BREADCRUMBS`），意思是"最多回溯用户报错前的 20 个操作"。

### 2. 为什么不能用数组

最直观的写法是这样：

```ts
const items = [];
function push(item) {
  items.push(item);
  if (items.length > 20) items.shift();   // 丢掉最老的
}
```

问题在 `shift()`：**它会把后面 19 个元素全部往前挪一格**，时间复杂度 O(n)。而且这个文件注释里点出了更隐蔽的问题：

> 每写满一次就要 slice 丢掉最老的，会产生大量临时数组，触发频繁 GC。

面包屑是**高频写入**的（每次点击、每个请求都写一条）。在一个交互密集的页面上，一秒可能写十几条。用数组方案，等于每秒制造十几个临时数组让垃圾回收器去扫 —— **监控 SDK 自己成了拖慢页面的元凶**，这就本末倒置了。

环形缓冲的解法：**定长数组 + 一个写指针**。写满之后直接覆盖最老的那一格，**写入永远是 O(1)，且从不分配新数组**。

### 3. 三个字段的分工（第 14–20 行）

```ts
private readonly items: Array<T | undefined>;
private writeIndex = 0;
private filled = 0;

constructor(private readonly capacity: number) {
  this.items = new Array<T | undefined>(capacity);
}
```

- **`items`**：定长数组，长度就等于容量。注意它是 `Array<T | undefined>` 而不是 `Array<T>` —— 刚创建时里面全是空洞，类型上必须诚实地标出来。
- **`writeIndex`**：下一个该写哪一格。写满后会绕回 0。
- **`filled`**：已经装了多少条，上限是 `capacity`。

**`filled` 为什么必须存在？** 这是这个文件最容易听漏的一点。

因为 `writeIndex` 会绕圈。当它等于 0 的时候，你没法判断这是「**刚开始写**」还是「**已经绕了一整圈**」——这两种状态要做的事完全不同（前者读数据要从下标 0 开始，后者要从 0 开始读的其实是"最老的那条"）。

所以环形缓冲天然需要区分**两个阶段**：

| 阶段 | 判断依据 | 语义 |
| --- | --- | --- |
| 填充期 | `filled < capacity` | 还没绕圈，数据从下标 0 起连续存放 |
| 稳态期 | `filled === capacity` | 已绕圈，最老的数据正好在 `writeIndex` 处 |

### 4. `push` 逐行（第 22–29 行）

```ts
push(item: T): void {
  this.items[this.writeIndex] = item;
  this.writeIndex = (this.writeIndex + 1) % this.capacity;
  if (this.filled < this.capacity) {
    this.filled += 1;
  }
}
```

- **第 1 行**：直接往当前指针位置覆盖。**注意这里没有任何"先判断格子有没有人"的逻辑** —— 覆盖就是设计本身，不是意外。
- **第 2 行**：`% capacity` 实现绕圈。写到最后一格后，`writeIndex` 回到 0。
- **第 3–5 行**：`filled` 封顶在 `capacity`。加 `if` 判断而不是无脑 `+= 1`，就是这个"封顶"动作。

### 5. `toArray` 逐行（第 31–42 行）—— **最容易讲错的地方**

```ts
toArray(): T[] {
  const start = this.filled < this.capacity ? 0 : this.writeIndex;
  const out: T[] = [];
  for (let i = 0; i < this.filled; i += 1) {
    const item = this.items[(start + i) % this.capacity];
    if (item !== undefined) {
      out.push(item);
    }
  }
  return out;
}
```

**第一行是整个方法的核心**，翻译成人话：

- **没写满**（填充期）：数据老老实实从下标 0 开始 → `start = 0`
- **写满了**（稳态期）：最老的那条**正好躺在 `writeIndex` 位置**（因为下一步它就要被覆盖了）→ `start = writeIndex`

第二行之后就是"从 `start` 出发，绕圈读 `filled` 个"。取模让下标自动回绕。

**`if (item !== undefined)` 这行看起来多余，其实有两个作用**：一是让 TypeScript 把类型从 `T | undefined` 收窄成 `T`；二是防住异常输入（比如有人传了负数或非整数容量，数组里就会出现真的读不到的位置）——**宁可少返回一条，也不要往看板上塞一个 `undefined`。**

### 6. 走位演示（实测数据）

容量设成 3，依次 push `a` `b` `c` `d` `e`。下面这张表是我真跑出来的：

| 操作 | `items` 实际内容 | `writeIndex` | `filled` | `toArray()` |
| --- | --- | --- | --- | --- |
| 初始 | `[_,_,_]` | 0 | 0 | `[]` |
| push a | `[a,_,_]` | 1 | 1 | `["a"]` |
| push b | `[a,b,_]` | 2 | 2 | `["a","b"]` |
| push c | `[a,b,c]` | 0 | 3 | `["a","b","c"]` |
| **push d** | `[d,b,c]` | 1 | 3 | `["b","c","d"]` |
| **push e** | `[d,e,c]` | 2 | 3 | `["c","d","e"]` |

**`push d` 那一行是最关键的一步**：

- `a` 被 `d` **直接覆盖**掉了（`items` 变成 `[d,b,c]`，注意顺序是乱的）
- `writeIndex` 变成 1，而 `filled === capacity`，所以 `start = 1`
- 读的时候从下标 1 开始绕：`1 → 2 → 0`，得到 `b, c, d` ✅

**内部存储顺序是乱的，但读出来永远是时间正序** —— 这就是环形缓冲的巧妙之处。看板的时间轴完全依赖这个保证，`toArray` 的注释里也写明了。

> ⚠️ 表里那个 `_` 在控制台里会显示成 `null`，那是 `JSON.stringify` 把 `undefined` 转成 `null` 的效果。
> **源码里数组装的是 `undefined`，不是 `null`。**

### 7. 复杂度与代价

| 操作 | 复杂度 | 是否分配内存 | 调用频率 |
| --- | --- | --- | --- |
| `push` | **O(1)** | **不分配** | 高频（每次点击/请求） |
| `toArray` | O(n)，n ≤ 20 | 每次新建数组 | **低频**（只在报错那一刻） |

**这里的取舍是刻意安排的**：把 O(n) 和内存分配**放在读取侧，而不是写入侧**。因为写入高频、读取低频。

如果反过来（写的时候 `slice`、读的时候直接返回），就等于把开销压在了最热的路径上 —— 面试时如果被问"这个设计有什么代价"，这就是正确答案：**代价是每次读取都要重建数组，但读取只在 `captureException` 冻结快照时发生一次。**

### 8. 这一节可能被追问什么

| 追问 | 怎么答 |
| --- | --- |
| 容量为什么是 20？ | 20 条足够回溯一段有意义的操作序列；再多会明显加大错误事件的体积（面包屑会随错误一起落盘） |
| `filled` 能不能用 `items.length` 代替？ | 不能，`items` 是预分配的定长数组，`length` 从头到尾都是 `capacity` |
| 满了丢最老的，可最新的不是最重要吗？ | 是，所以丢的是**最老的**。重要的历史已经被 `captureException` 冻结成快照了 |
| 为什么干脆不用 Map 做成 LRU？ | LRU 要维护链表和驱逐逻辑，代码量和体积都更大。这里存在意义只是"最近 N 条"，不需要按 key 查 |
| 这个数据结构在生产里还有别的地方用吗？ | 有，日志环形缓冲、音视频帧缓冲、终端回滚缓冲都是同一个套路 |

## 第三部分 · 两个文件怎么配合

```
① 用户在页面上点了按钮
        ↓
   breadcrumbs.ts 监听到 → client.addBreadcrumb()
        ↓
   RingBuffer.push()    ← 高频路径：O(1)、零分配
        ↓
② 某个时刻报错了
        ↓
   client.captureException() 调用 getBreadcrumbs()
        ↓
   RingBuffer.toArray()  ← 低频路径：复制一份快照出来
        ↓
   快照挂到 error 事件的 breadcrumbs 字段上（client.ts:182）
        ↓
③ client.captureEvent() —— 这里才第一次用到 sampling.ts 的结论
        ↓
   if (!this.sampled) return;   ← 采样决策拦在这里
        ↓
   进队列 → flush → IndexedDB 落盘
```

两个文件在链路上的位置是**一前一后**的：

- **`ring-buffer.ts` 管「采了之后临时记在哪」** —— 它是写入侧的前置缓存
- **`sampling.ts` 管「这个东西到底要不要采」** —— 它是写入侧的最终闸门

它们在 `client.ts` 里相遇，但互不依赖 —— 这也是为什么这两个文件都能被单独单元测试。

## 第四部分 · 面试速答卡

背下这六句，被问到这两个话题都能接住：

| 话题 | 30 秒版本 |
| --- | --- |
| **采样粒度** | 「采样必须按会话做，不能按事件做。按事件抽签会把用户的因果链剪碎 —— 你看到一个错误，但看不到导致它的那次操作。」 |
| **稳定采样的实现** | 「对 sessionId 做 djb2 哈希，映射到 0~1 和采样率比较。纯函数，不存任何状态，同一个会话永远得到同一结果。」 |
| **哈希的局限** | 「djb2 对短输入扩散很弱，实测两个字符的 ID 全落在同一个桶里。所以我保证生成的 sessionId 有 20 个字符、带随机后缀。」 |
| **环形缓冲的动机** | 「面包屑是高频写入的，用数组 + shift 每次都要搬移元素还会制造临时数组。环形缓冲是定长数组加写指针，写入 O(1) 且零分配。」 |
| **`filled` 的作用** | 「写指针会绕圈，绕回 0 时分不清是刚开始还是绕了一圈，所以需要 `filled` 区分填充期和稳态期。」 |
| **读顺序的保证** | 「内部存储顺序是乱的，但 `toArray` 从最老的位置起绕圈读，保证时间正序 —— 看板的时间轴依赖这个。」 |
